# 食光有数 · 试点准备包

> 对应执行书任务 12。本文档用于首个供餐周期的试点准备，**不涉及代码变更**。
> 首轮范围：1 个食堂、1–2 个档口、1 个午餐时段。

---

## 1. 试点范围与前置条件

| 项 | 首轮取值 | 确认人 |
|---|---|---|
| 食堂 | 待定（建议凯风餐厅或荔山餐厅） | 项目负责人 |
| 档口 | 1–2 个，需能独立接单 | 档口负责人 |
| 餐次 | 午餐（11:30–12:15 三个时段） | 食堂经理 |
| 供应日 | 连续 5 个工作日（周一至周五） | 项目负责人 |
| 参与学生 | 20–50 人（小范围） | 项目负责人 |
| 付款方式 | 到店付款（平台不做在线支付） | 财务 |

**进入试点前必须全部为"是"**：

- [ ] 档口已完成菜单录入，价格与窗口一致
- [ ] 每个菜品标了「辣度 / 油腻 / 咸度」，过敏原已勾选
- [ ] 库存数量按日均供应量设置，售罄可自动拦截
- [ ] 取餐时段容量按档口出餐能力设置（建议 20–30 单/时段）
- [ ] 商户账号已绑定档口（`Stall.managers`）
- [ ] 核销人员会用「取餐码核销」页面
- [ ] 已配置暂停开关的操作人

## 3. 菜单与饮食标签核验表

**逐菜核对**，由档口负责人与项目负责人双签。数据来自线上后台「菜品管理」。

| 菜品 | 价格（元） | 分类 | 辣度 0-5 | 油腻 0-5 | 咸度 0-5 | 素食 | 高蛋白 | 过敏原 | 核验人 |
|---|---|---|---|---|---|---|---|---|---|
| | | | | | | | | | |

**核验要点**：

1. **价格必须与窗口一致**。平台按下单时的价格快照结算，事后改价不影响历史订单。
2. **辣度/油腻/咸度不是装饰**。推荐的「口味匹配」直接读这三个值，填错会导致推荐偏。
3. **过敏原是硬过滤**。标了"花生"的菜，对花生过敏的学生永远看不到——漏标是安全风险。
4. **素食标记影响纯素学生**。`VEGETARIAN` 只看 `isVegetarian`；`VEGAN`/`HALAL`/`PESCATARIAN` 需要额外的核验字段，未核验的菜一律不推荐。

## 4. 三角色操作手册

### 4.1 学生

| 场景 | 操作 | 预期结果 |
|---|---|---|
| 首次使用 | 注册 → 3 步设置口味（约 1 分钟） | 首页出现个性化推荐，附推荐理由 |
| 今天吃什么 | 首页「换一批」或点场景标签（想吃辣/清淡/高蛋白…） | 推荐 3 道菜，每道有「为什么推荐它」 |
| 下单 | 选菜 → 选取餐时段 → 确认提交 | 生成订单号与取餐码，库存扣减 |
| 取餐 | 到档口报取餐码 | 商户核销，订单变「已取餐」 |
| 评价 | 订单详情 → 评价 → 10 星打分 + 体感标签 | 评分实时影响该菜星级与下一次推荐 |
| 临时有事 | 订单详情 → 取消 | 截止前可取消，库存与名额返还 |

**遇到问题**：

- **推荐为空** → 检查口味设置里的预算是否过窄（如上限 ¥5），或当前时段无供应
- **时段不可选** → 该时段已过截止时间（默认提前 15 分钟）
- **菜品显示售罄** → 库存已扣完，换一道或换档口

### 4.2 商户

| 场景 | 操作 | 注意事项 |
|---|---|---|
| 发布菜单 | 后台「菜单管理」→ 选日期餐次 → 挂菜品 | 发布后学生端立即可见 |
| 设置库存 | 每个菜品设 `total` | 库存扣到 0 自动售罄 |
| 设置时段容量 | 「取餐时段」→ 设置 capacity | 容量满了学生选不到该时段 |
| 接单备餐 | 「待处理订单」→ 标记备餐中 | 状态流转：待取餐 → 备餐中 |
| 核销 | 输入或扫码取餐码 | **一码只能核销一次**，重复提示"已核销" |
| 停售某菜 | 菜品管理 → 下架 | 已下单的订单不受影响 |
| 恢复停售 | 菜单管理里找到已下架项 → 上架 | 若列表看不到停售项，需按档口查询（见"已知限制"） |

### 4.3 管理员

| 场景 | 操作 |
|---|---|
| 档口授权 | 为用户分配 `MERCHANT` 角色并绑定档口 |
| 查看经营数据 | 「经营统计」按营业日、档口、订单状态聚合 |
| 评价审核 | 隐藏违规评价（`status: HIDDEN`） |
| 操作审计 | 查看 `AuditLog`：改角色、改菜品、审核记录 |
| 紧急暂停 | 见第 7 节 |

## 5. 异常处理

| 现象 | 判断 | 处置 |
|---|---|---|
| 学生下单报"库存不足" | 最后一份被同时抢走 | 提示换菜；**不要手工改库存**，让系统状态自洽 |
| 订单显示已取消但仍扣库存 | 数据不一致 | 记录订单号，暂停该档口新预约，人工核对 `Inventory` |
| 同一取餐码核销两次 | 并发或重复点击 | 检查订单状态；只有第一次应成功，第二次应返回"已核销" |
| 学生说"我的订单不见了" | 可能登录了别的账号 | 用邮箱核对 `User.email`；不要跨账号查订单 |
| 推荐结果明显不对 | 口味画像或菜品标签有误 | 查该学生的 `UserPreference` 与菜品三维评分，修标签后让学生「重置画像」 |
| 页面 502 | nginx upstream 指向旧容器 | 重启 proxy（容器重建后必做） |
| 登录后立刻退回登录页 | Cookie 被浏览器丢弃 | 检查 `COOKIE_DOMAIN` 是否写死、`COOKIE_SECURE` 与访问协议是否匹配 |

## 6. 数据指标口径

**统计窗口**：按**上海时间营业日**（00:00–24:00）切分，不按 UTC、不按自然周。

| 指标 | 分子 | 分母 | 备注 |
|---|---|---|---|
| 有效预约成功率 | 创建成功且未被系统取消的订单数 | 提交的预约请求数（**按幂等键去重**） | 学生重复点击只算 1 次 |
| 取餐完成率 | 状态为 `PICKED_UP` 的订单数 | 有效预约数 | |
| 取消率 | 学生主动取消（`CANCELLED`）的订单数 | 有效预约数 | 不含系统超时关闭 |
| 过期率 | 系统超时关闭（`EXPIRED`）的订单数 | 有效预约数 | 反映"约了不来" |
| 库存冲突次数 | 下单时因库存不足被拒的次数 | 提交的预约请求数 | 反映备货不足 |
| 人工处理次数 | 商户/管理员手动干预的订单数 | 有效预约数 | 需要人工记录，系统不自动统计 |
| 推荐转化率 | 「看过推荐且下单了推荐菜品」的学生数 | 看过推荐的学生数 | 与同餐次热门菜基线对比 |

**基线对照**：试点期间保留"同餐次热门菜"作为对照，用于判断推荐是否真的优于"随便点"。

## 7. 暂停与恢复

### 7.1 立即暂停的条件（满足任一即暂停新预约）

1. **数据丢失**：订单、库存或评价出现无法解释的缺失
2. **越权**：商户能改到别人档口的菜，或学生看到后台数据
3. **负库存**：任何菜品库存出现负数
4. **重复核销**：同一取餐码被核销两次且都成功

### 7.2 暂停操作路径

**当前版本没有一键暂停开关**，用以下方式阻断新预约：

1. 后台把所有档口的**取餐时段容量改为 0**（学生选不到时段，无法下单）
2. 或后台把当日菜单**取消发布**（`status: DRAFT`）

**已有订单仍可履约或取消** —— 暂停只阻断"新预约"，不阻断"取餐"和"取消"。

### 7.3 恢复条件

| 暂停原因 | 恢复前提 |
|---|---|
| 数据不一致 | 人工核对后修正，并记录到异常台账 |
| 越权 | 修复权限并回归验证（跨档口请求应 403） |
| 负库存 | 修正库存并确认扣减逻辑无重复 |
| 重复核销 | 修复条件更新逻辑并验证并发 |

## 8. 已知限制（试点前需告知参与方）

| 限制 | 影响 | 临时方案 |
|---|---|---|
| 无在线支付 | 只能到店付款 | 明确告知学生"下单不等于付款" |
| 商户端看不到已停售菜品（若走默认列表） | 停售后无法从原入口恢复 | 用档口维度的管理列表查询 |
| 评价补评限频 24 小时 3 条 | 密集测试时会被拦 | 用不同订单测试 |
| 推荐对小样本敏感 | 前几条评价会明显改变排序 | 试点初期不要过度解读排序波动 |
| 无邮件/短信通知 | 只能站内查看 | 商户定时刷新待处理列表 |
