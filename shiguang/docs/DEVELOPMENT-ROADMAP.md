# 食光有数后续开发路线图

下一版的目标是交付**可重复部署的演示版**，并在此基础上达到**真实校园试点的条件**。首轮试点建议从一个食堂、1–2 个档口和一个午餐时段开始，验证学生选餐、预约、取餐、评价和下一次推荐的完整链路。

本计划按 3–4 人并行、约 6 周估算。实际试点日期取决于档口配合和数据准备。各阶段以验收结果作为进入下一阶段的依据。

## 第 1 周 · 建立安全、可复现的发布基线

- **版本和构建。** 将源码、迁移、运行资源与 `pnpm-lock.yaml` 纳入 Git，修正误伤上传模块的忽略规则，把 CI 工作流移到仓库根目录。统一冻结依赖安装，修复 Compose、Azure 脚本和本地同源 API 转发。从通过 CI 的提交生成发布包，附提交号和校验和。 [忽略规则](../.gitignore#L9) · [CI](../.github/workflows/ci.yml#L39) · [Compose](../docker-compose.yml#L79) · [Azure 部署脚本](../azure/deploy-app.sh#L150)
- **数据库保护。** 移除启动、重启和部署中的自动演示数据初始化。将演示数据改为在专用数据库中显式、幂等地初始化。生产启动时校验演示开关、安全 Cookie 和密钥，停用已有的演示特权账号并撤销会话。 [演示数据](../prisma/seed.ts#L150) · [容器入口](../scripts/entrypoint-api.sh#L7)
- **权限与响应边界。** 菜品更新采用运行时 DTO，逐项映射允许写入的字段。梳理学生、商户、管理员的权限矩阵，检查写接口的角色及档口范围。用户相关接口显式选择响应字段，审计记录保留角色、操作和目标。 [菜品更新](../apps/api/src/dishes/dishes.module.ts#L111) · [用户资料](../apps/api/src/users/users.module.ts#L25)

**阶段验收**　全新检出可冻结安装并构建，开发、生产和 Tunnel 三套 Compose 配置及 Shell 语法检查通过。用含历史用户、订单和审计记录的测试库执行升级和重启，确认数据保留。越权请求返回 403，额外写入字段返回 400，用户响应中无密码散列。

## 第 2–3 周 · 稳定订单、取餐和评价

- **统一供餐上下文。** 用 `Asia/Shanghai` 计算营业日、餐次和截止时刻。以服务端取餐时段为订单日期、餐次和档口的依据，在事务内重验菜单、库存和名额。若结算价格与购物车展示不同，让学生重新确认。 [订单服务](../apps/api/src/orders/orders.module.ts#L48) · [结算页](../apps/web/src/app/checkout/page.tsx#L26)
- **收拢订单状态流转。** 下单、取消、核销和超时统一使用条件更新。状态成功迁移后，在同一事务内扣减或释放库存、调整名额、更新凭证并写入通知。明确已备餐订单取消后的处理规则。幂等键按账号和请求内容匹配，同内容重试返回原订单，改动内容后复用键返回冲突。 [取餐服务](../apps/api/src/pickup/pickup.module.ts#L101) · [超时任务](../apps/api/src/tasks/tasks.module.ts#L72)
- **保护评价与历史数据。** 将补评限频、评价写入和均分重算纳入一致的并发策略。为画像重置记录生效时间，后续重放以该时间为起点。新增数据库约束前，先检查历史订单的时段错配、重复记录和异常库存，再分批回填。历史金额以成交快照核算。 [评价服务](../apps/api/src/reviews/reviews.module.ts#L137) · [画像重置](../apps/api/src/preferences/preferences.module.ts#L97) · [数据库说明](DATABASE.md)

**阶段验收**　用真实 PostgreSQL 验证 20 个并发请求争抢最后一份时仅一单成功，同一幂等键并发只生成一单，双取消只释放一次，取消与核销竞争只产生一个终态。覆盖跨日、截止前后、未来预约、重复核销和画像重置后的新评价。

## 第 4 周 · 完成三类角色的演示闭环

| 工作线 | 交付内容 |
| --- | --- |
| 学生端 | 推荐、菜单和结算沿用同一供餐上下文。明确展示售罄、时段失效、价格变动和会话过期，并提供相应的恢复操作。统一处理 CSRF、表单上传和请求错误，账号停用成功后再跳转。补齐评价筛选、菜品分页和移动端可用性。 |
| 商户与管理端 | 商户可发布菜单、设置库存和容量、恢复停售菜品、查看待处理订单并核销。管理员负责档口授权、评价审核和操作审计。日报按营业日、订单状态和档口范围聚合，分别统计预约、完成、取消和过期。 |
| 推荐与画像 | 单菜和套餐共享可售与饮食筛选规则，套餐严格受总预算约束。严格饮食模式只纳入经过核验的菜品。推荐理由引用实际生效条件，权重配置持久化并记录版本。用固定样本验证预算、餐次、饮食条件及反馈后的排序变化。 |

**阶段验收**　用隔离数据跑一遍学生下单、商户备餐与核销、学生评价、推荐更新。浏览器用例实际创建订单，并断言库存、凭证状态和推荐变化。演示交付提供启动说明、三角色操作手册和可重复初始化的数据。 [推荐算法](RECOMMENDATION.md) · [现有 E2E](../tests/e2e/student-flow.spec.ts#L17) · [用户手册](USER_GUIDE.md)

## 第 5–6 周 · 预发布验证与小范围试点

- **部署与恢复。** 选定一条生产部署路径，在预发布环境验证 HTTPS、CSRF、端口隔离和会话。演练从备份恢复 PostgreSQL 和上传图片，再验证旧版应用与迁移后数据库的兼容性。分别检查进程存活、依赖就绪和订单超时任务，保留下单、核销及备份失败的告警。 [部署说明](DEPLOYMENT.md) · [备份脚本](../scripts/backup.sh) · [恢复脚本](../scripts/restore.sh)
- **试点准备。** 由参与档口确认菜品、价格、供应时间、库存和饮食标签，培训接单、备餐、核销和异常处理。先邀请少量学生完成一个午餐供餐周期，再根据实测情况扩大。出现数据丢失、越权、负库存或重复核销时，暂停新预约，已有订单仍可履约或取消。
- **衡量结果。** 每日记录有效预约成功率、取餐完成率、取消和过期率、库存冲突及人工处理次数。推荐效果先记录「看到推荐且预约了推荐菜品的学生占比」，再与同餐次热门菜基线对比。根据首批数据决定下一轮优先优化供餐准确性、结算转化还是推荐排序。

**阶段验收**　HTTPS、数据库和图片恢复、应用回退均有演练记录。至少完成一个午餐供餐周期，试点记录可按档口追溯订单异常与人工处理结果。

## 分工与后续扩展

| 工作线 | 首轮任务 |
| --- | --- |
| 工程交付 | Git、锁文件、CI 和部署校验 |
| 后端 | 数据保护、权限边界和订单状态流转 |
| 前端与测试 | 定义三角色验收场景，补充接口回归和浏览器闭环 |

每项任务完成时附可复现用例和验收证据。涉及数据库的任务附迁移、回填与回退说明。

首个迭代优先安排**可复现源码基线、移除自动清库、修复越权写入、补齐订单并发测试**。

试点稳定后，按运营需求评估校园统一认证、食堂菜单同步和支付接入。推荐先积累真实预约与评价数据，再决定是否引入更复杂的排序模型。
