# 可迁移经验卡片（LESSONS）

> 与 `RETROSPECTIVE.md` 的分工：那份是**叙事**（时间线 + 反思），这份是**卡片**（按"遇到什么问题"检索）。
> 每张卡片：**现象 → 根因 → 原则 → 怎么用**。编号 L-xx 便于在讨论中引用。

---

## 一、数据

### L-01 · 假数据比没数据更危险

**现象**：为了赶进度，用 56 道假菜名撑着推荐功能。换成真实数据后，口味选项、价格区间、档口结构全部对不上，整套逻辑返工。

**根因**：假数据让"看起来能跑"掩盖了"设计假设是错的"。

**原则**：**先有真数据，再设计功能**。数据决定选项，不是反过来。

**怎么用**：新项目第一周就把真实数据录进去（哪怕只录一个食堂），然后用它反推该有哪些筛选项、该分几档价格。

---

### L-02 · 清理数据的脚本必须幂等

**现象**：`seed.ts` 用 `TRUNCATE` + `create`，每次跑都清库重建。部署后容器重启自动跑了一次，**所有用户数据丢失**。

**根因**：把"初始化"和"重置"混为一谈。

**原则**：**初始化用 `upsert`（有则更新、无则创建），重置必须是显式操作**。

**怎么用**：
```ts
// ❌ 会清库
await prisma.dish.deleteMany();
await prisma.dish.create({ data: {...} });

// ✅ 幂等
await prisma.dish.upsert({
  where: { id },
  create: {...},
  update: {...},
});
```

---

### L-03 · 数据库层的"自动字段"在裸 SQL 里不存在

**现象**：用 SQL 往 `Inventory` 插数据，报 `null value in column "updatedAt"`。

**根因**：Prisma 的 `@updatedAt` 是**应用层行为**，数据库表里这一列**没有默认值**。

**原则**：**ORM 的"自动行为"只在使用 ORM 时存在**。绕过 ORM 就要手动补。

**怎么用**：裸 SQL 插入时，`createdAt` / `updatedAt` 显式给 `now()`。

---

### L-04 · 时区要分清三个概念

**现象**：SQL 里 `(now() + interval '8 hours')::date` 生成菜单，结果全跑到了明天。

**根因**：这个项目里同时存在三套时间：
- **数据库会话时区**：`Asia/Shanghai`（`now()` 已是北京时间）
- **Node 进程时区**：UTC
- **业务函数**：手动 `+ 8 小时`（`campusDate`）

三套并存，每加一次 8 小时就错一天。

**原则**：**时区只在边界转换一次**，内部统一用一种时间表示。

**怎么用**：
- 写 SQL 时用 `CURRENT_DATE`，别手动加偏移
- 应用层统一调 `campusDate(now)`，禁止裸用 `new Date().getDate()`
- 定一条规矩写进 ADR："任何地方需要营业日，只能来自 `campusDate`"

## 二、测试

### L-05 · 单元测试测不出权限漏洞

**现象**：菜品编辑接口允许商户改 `stallId`（把菜挂到别人档口），代码审查和单测都没发现。

**根因**：`Partial<DishDto>` 的类型约束让**写测试代码时就传不进非法字段**——编译器挡住了"模拟攻击"。

**原则**：**安全类问题必须用集成测试 + 强制类型绕过**（`as never`）才能验证。

**怎么用**：
```ts
const payload = { name: 'xxx', stallId: otherStallId } as never;  // 绕过类型
const result = await service.update(merchant, dishId, payload);
expect(result.stallId).toBe(ownStallId);  // 断言没事
```

---

### L-06 · 测试"跳过"会伪装成"全绿"

**现象**：集成测试显示 `1 passed | 1 skipped`，看起来没问题，其实**20 个用例一个都没跑**。

**根因**：`describe.runIf(Boolean(dbUrl))`，没设环境变量就静默跳过。

**原则**：**跳过必须显式告警**。CI 里应该把"skip 数量"也作为检查项。

**怎么用**：
- 本地跑测试时看 `Tests N passed | M skipped`，M > 0 要追问为什么
- CI 里加一步：`skipped > 0 && exit 1`（对关键套件）

---

### L-07 · 测试库要有名字白名单

**现象**：写集成测试脚本时，担心某个同事把 `ORDER_TEST_DATABASE_URL` 配成生产库，一跑就把真实数据 `TRUNCATE` 了。

**原则**：**危险操作的入口要做"防呆"**，而不是靠人记得。

**怎么用**：
```ts
// 库名必须以 _test 结尾，否则直接拒绝运行
if (!/^\/[a-z][a-z0-9_]*_test/.test(new URL(url).pathname)) {
  throw new Error('必须指向专用测试库');
}
```

## 三、部署

### L-08 · 改了镜像内的文件必须重建镜像

**现象**：改了 `seed.ts` 传到服务器，`docker compose exec api pnpm exec tsx prisma/seed.ts` 跑的**还是旧代码**，报错位置一模一样。

**根因**：`exec` 在**已运行的容器**里执行，容器用的是**镜像里的文件**，不是宿主机的。

**原则**：**"宿主机文件"和"容器内文件"是两个世界**。

**怎么用**：
```bash
docker compose build api    # 重建镜像
docker compose up -d api    # 用新镜像重建容器
docker compose exec -T api grep 新代码特征 apps/...  # 验证真的更新了
```

---

### L-09 · 容器重建后必须重启 nginx

**现象**：api 容器重建后，站点 502。

**根因**：nginx 启动时把后端 IP 缓存了，容器重建后 IP 变了。

**原则**：**任何依赖"服务发现"的组件，在上游变化后都要刷新**。

**怎么用**：部署脚本里把 `restart proxy` 作为固定步骤，不要靠记。

---

### L-10 · 前端"公开"环境变量是构建期写死的

**现象**：改了 `NEXT_PUBLIC_API_BASE_URL` 重启容器，页面请求的地址没变。

**根因**：Next.js 在 `next build` 时把 `NEXT_PUBLIC_*` **内联进 JS 文件**，运行时改环境变量无效。

**原则**：**区分"构建时配置"和"运行时配置"**。

**怎么用**：要运行时可变的东西，做成服务端接口返回，不要用 `NEXT_PUBLIC_`。

---

## 四、安全

### L-11 · 类型系统不是运行时校验

**现象**：`async update(dto: Partial<DishDto>)` 看起来类型安全，实际运行时 metatype 是 `Object`，NestJS 的 `ValidationPipe` **整个跳过**，请求体里塞什么字段都行。

**根因**：TypeScript 的类型**编译后擦除**，运行时没有任何约束。

**原则**：**从前端来的数据，必须在运行时再校验一次**。

**怎么用**：
- DTO 必须是**真实类**（带 `class-validator` 装饰器），不能用 `Partial<T>` / `Record<string, any>`
- Service 层再加一层**字段白名单**，双保险

---

### L-12 · 响应要显式 select

**现象**：`prisma.user.update()` 直接返回，结果把 `passwordHash` 一起吐给前端。

**根因**：Prisma 默认返回**所有字段**。

**原则**：**返回给用户的数据要"白名单化"**，不是"黑名单化"。

**怎么用**：所有涉及 `User` 的查询都显式 `select: { id, email, displayName, ... }`，排除密码哈希。

---

### L-13 · Cookie 三件套，任一配错都是"登录不了"

**现象**：评审平台只给 IP，站点登录后立刻退回登录页。排查发现三个问题叠加。

| 属性 | 错法 | 后果 |
|---|---|---|
| `Secure` | 设为 true 但访问是 HTTP | 浏览器不保存 |
| `Domain` | 写死域名但用 IP 访问 | 浏览器直接丢弃 |
| `SameSite`/CSRF | 双提交依赖 Cookie | 前两个坏时跟着坏 |

**原则**：**配置类问题按数据流向逐层验证**（生成 → 传输 → 接收 → 回传 → 识别）。

**怎么用**：
```bash
curl -s -i -X POST http://IP/api/v1/auth/login ... | grep -i set-cookie
# 必须既没有 Secure 也没有 Domain=
```

## 五、调试

### L-14 · "返回 0"不等于成功

**现象**：`docker exec mydb psql <<'SQL' ... SQL` 返回 0，日志说"已插入 3 条"，但表里 0 行。

**根因**：`docker exec` **缺 `-i`**，heredoc 没传进容器，psql 空跑也返回 0。

**原则**：**任何"看起来执行了"的操作，都要立刻查一次真实状态**。

**怎么用**：
```bash
docker exec -i mydb psql ...   # 必须带 -i
# 然后立刻：SELECT count(*) 验证
```

---

### L-15 · `DO $$` 块是单事务，报错就全回滚

**现象**：跑了补菜单的 SQL，输出 `DO` 没有任何报错，但数据一条没增加。

**根因**：`DO $$ ... $$` 中间有一行 `m.id || i`（text || integer 类型不匹配）→ **整个块回滚**，但 `psql` 只返回最后一行 `DO`。

**原则**：**批量 SQL 必须看 `NOTICE` 输出，不能只看返回码**。

**怎么用**：
```sql
SET client_min_messages TO NOTICE;
DO $$ BEGIN RAISE NOTICE '开始 %'; ... END $$;
-- 要看到 NOTICE 才算真的执行了
```

---

### L-16 · 自动化改代码必须限次数

**现象**：用 Python 批量插入一段代码，结果被插了两遍，第 7 个 `create` 撞唯一约束 → seed 事务回滚 → 菜单/评价全没生成。

**根因**：`str.replace(old, new)` **默认替换所有匹配**。

**原则**：**任何自动修改文件的操作，都要断言"只匹配一处"**。

**怎么用**：
```python
assert s.count(old) == 1, f'匹配 {s.count(old)} 次'
s = s.replace(old, new, 1)
```
更进一步：锚点要用**包含函数名的长上下文**，不要用单条语句。

---

### L-17 · 分层定位比读代码快

**现象**：推荐显示 0 道，第一反应是"算法有 bug"。

**实际排查顺序**（5 分钟定位）：
1. 数据在不在 → `SELECT count(*) FROM "Dish"` → 59 条，数据没问题
2. 当天的菜单在不在 → `SELECT count(*) FROM "Menu" WHERE date = CURRENT_DATE` → **0 条**
3. 结论：不是算法问题，是"今天没菜单"

**原则**：**先确认数据，再怀疑逻辑；先看现象，再读代码**。

**怎么用**：建立一个"从外到内"的检查清单：网络 → 服务 → 数据 → 逻辑。

## 六、文档

### L-18 · 文档过期比没有更糟

**现象**：`TESTING.md` 写着"27/27 通过、集成测试未运行"，实际早已 45+20 全过。`DATABASE.md` 写"3 食堂/54 菜"，实际 13/59。

**根因**：文档最后集中写，之后代码改了没同步。

**原则**：**文档与代码同一次提交里改**，不留"待更新"。

**怎么用**：PR 模板加一行"本次改动涉及的文档是否已更新"，勾选才能合并。

---

### L-19 · 文档要分层，缺一层就有盲区

| 层 | 面向 | 缺了会怎样 |
|---|---|---|
| 产品（PRD） | 评审 | 不知道"为什么做"、边界在哪 |
| 决策（ADR） | 技术负责人 | 半年后想改方向，不知道当初为什么这么选 |
| 设计（架构/数据/API） | 开发 | 新人看不懂代码结构 |
| 操作（用户/运维） | 用户、运维 | 不会用、出问题不会查 |
| 过程（CHANGELOG/交接） | 接手的人 | 不知道踩过哪些坑，会重踩 |

**原则**：**文档按"读者是谁"分层，不是按"内容多少"堆一起**。

## 七、与 AI 协作

### L-20 · AI 的"应该没问题"不算证据

**现象**：让 AI 改代码，它说"已修复，应该没问题"。实际一跑就报错。

**原则**：**只接受可复现的证据**——命令输出、测试结果、行数、接口返回。

**怎么用**：
- 要求"改完跑一遍 tsc / 测试，把输出贴出来"
- 关键操作后立刻验证真实状态，不信"已完成"的自我报告
- AI 说"应该"的时候，就是在猜

---

### L-21 · 让 AI 审查就只审查

**现象**：要求"检查这段代码有没有问题"，AI 顺手把代码改了，掩盖了原始问题。

**原则**：**审查和修改是两个动作，要分开授权**。

**怎么用**：明确说"只读检查，列出问题，不要改"；确认问题后再单独授权修改。

---

### L-22 · AI 擅长"执行"，不擅长"判断该不该做"

**现象**：AI 能快速实现一个功能，但"这个功能该不该做""这个方案有什么代价"，需要人拍板。

**原则**：**技术选型、架构变更、范围取舍由人决定**，AI 提供选项和代价分析。

**怎么用**：让 AI 输出"方案 A 的代价是…，方案 B 的代价是…"，你选。
