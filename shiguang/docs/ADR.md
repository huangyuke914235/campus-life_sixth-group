# 架构决策记录（ADR）

> 每条记录一个**已经做过、且影响深远**的技术选择。格式：背景 → 决策 → 理由 → 代价。
> 新人接手或想改方向时，先读这里，避免重复讨论。

---

## ADR-001 · 前后端分离，Next.js + NestJS 两个应用

**背景**：一个校园小工具，团队 3–4 人，需要同时支持学生端、商户端、管理端。

**决策**：`apps/web`（Next.js）只做 UI 与同源转发，`apps/api`（NestJS）承担全部业务逻辑。

**理由**：
- 三类角色权限差异大（学生/商户/管理员），后端集中做鉴权比在 Next 的 Server Actions 里散落更可控
- 推荐算法要复用到「首页推荐」「搭配页」「结算页」，放在后端一处实现，前端只消费
- 未来若要做小程序 / App，API 可直接复用

**代价**：
- 两套进程、两套构建，部署复杂度上升
- 本地开发要同时起 3000（web）和 3001（api），靠 nginx 或 next rewrites 打通

## ADR-002 · 推荐算法本地实现，不调用大模型

**背景**：2026 年做推荐，直觉是用 LLM 生成理由。

**决策**：七维加权打分（`packages/shared/src/recommendation.ts`），**纯本地计算，零外部 API**。

**理由**：
- **可解释性**：每个理由必须追溯到具体偏好字段（"你设的预算 15–25 元"），LLM 生成的理由无法保证不编造
- **确定性**：同一输入必须得到同一输出，否则无法测试、无法复现问题
- **成本**：饭点每小时上千次请求，调用 LLM 的成本无法接受
- **离线**：食堂网络不稳定，依赖外部 API 会让核心功能在断网时瘫痪

**代价**：
- 理由文案是模板化的，多样性不如 LLM
- 冷启动依赖问卷，问卷质量直接决定推荐质量

**何时该重新考虑**：积累超过 10 万条真实评价后，可考虑用协同过滤替换/补充权重模型——但仍不建议用生成式模型产出理由。

## ADR-003 · 评分用 10 星，不用 5 星

**背景**：主流评价体系是 5 星。

**决策**：1–10 分。

**理由**：
- 5 星制下用户倾向集中打 4 星（"还不错"），方差太小，无法区分"能吃"和"很好吃"
- 10 星制能拉开区分度，配合贝叶斯平滑（先验 7.0 / 权重 10）后，单个极端评分不会刷榜
- 菜品评价粒度本来就该更细：口味、油腻、咸度是三个独立维度，5 星不够分

**代价**：
- 用户第一眼会觉得"10 星好奇怪"
- 前端要提供明确的档位提示（差 1–3 / 一般 4–7 / 好评 8–10）

**踩过的坑**：评价广场的「8–10 分好评」筛选曾经失效，因为 `@Query('minRating')` 拿到的是 string，Prisma 对 Int 字段做 `gte: '8'` 静默不生效。**任何从 query 取的数字都要显式 `Number()`**。

## ADR-004 · 只用 Cookie 认证，不用 Bearer Token

**背景**：SPA 常见做法是把 token 放 localStorage 用 `Authorization: Bearer`。

**决策**：`access_token` / `refresh_token` / `csrf_token` 三个 HttpOnly Cookie + 双提交 CSRF。

**理由**：
- 同源部署（nginx 同时服务前端和 API），Cookie 天然可用，不需要处理跨域
- localStorage 存 token 有 XSS 风险，Cookie + HttpOnly 免疫
- 双提交 CSRF 不需要服务端存 session，比 CSRF token 存 Redis 轻

**代价（这是本项目最大的运维坑）**：
- **IP 访问必须满足三个条件**才能登录：`COOKIE_SECURE=false`（HTTP 下浏览器才存）、`COOKIE_DOMAIN` 留空（否则 IP 与域名不匹配被丢弃）、`CSRF_ENABLED=true` 且前端带上 `X-CSRF-Token`
- 评审平台只给 IP 时，这三个条件缺一个就表现为"登录成功但立刻退回登录页"

## ADR-005 · 演示数据与生产数据严格隔离

**背景**：早期为了演示方便，容器启动时自动跑 seed。

**决策**：**移除所有自动 seed**，演示数据只在专用库显式初始化。

**理由**：
- `seed.ts` 开头是 `TRUNCATE ... CASCADE`，一旦在生产容器里跑，**所有用户、订单、评价瞬间清空**
- 已经因此丢过一次数据（部署后重启，数据回到初始状态）
- 演示数据的价值只在"第一次展示"，之后真实数据才是资产

**代价**：
- 换环境要手动跑一次 seed
- 菜单不会自动更新（见 ADR-006）

**现有防护**：`runtime-config.ts` 在 `NODE_ENV=production` 时**拒绝** `SEED_DEMO_DATA=true`，无豁免口子。

## ADR-006 · 菜单按「日期 + 餐次」建模

**背景**：菜单是否该跟着日期走？

**决策**：`Menu` 的唯一键是 `[stallId, date, mealType]`，库存 `Inventory` 同样按天独立。

**理由**：
- 食堂真实运营就是"今天卖什么、明天可能不一样"
- 库存必须按天重置，否则昨天的剩余会影响今天
- 取餐时段也要按天，跨天的时段没有意义

**代价（当前最大的产品缺口）**：
- **隔天不发布新菜单，推荐就空**。`loadCandidates` 按当天查，查不到直接返回 0 道
- 目前靠手工 SQL 把菜单复制到未来 30 天规避
- **正确解法**是商户端提供「一键复制昨日菜单」，这是下一步要补的功能

## ADR-007 · 订单状态用条件更新，不用悲观锁

**背景**：并发下单会超卖，并发核销会重复。

**决策**：全部用 `updateMany({ where: { id, status: 期望值 } })` + `count === 1` 判定，外层包 `withSerializable` 事务。

**理由**：
- 悲观锁（`SELECT FOR UPDATE`）在 Prisma 里要写原生 SQL，且容易死锁
- 条件更新是"乐观"的：只有状态符合预期才更新，天然幂等
- 配合可串行化隔离级别，20 并发下已验证只有 1 单成功

**代价**：
- 可串行化事务在冲突时会抛 `40001`，需要重试逻辑（现有实现靠 Prisma 自动重试）
- 高并发下吞吐不如乐观锁 + 版本号，但校园场景（峰值几十并发）完全够

**验证**：`scripts/verify-integration.sh` 覆盖 20 并发抢库存 1、抢名额 1、双取消、双核销。

## ADR-008 · 时区统一用 Asia/Shanghai 的工具函数

**背景**：服务器是 UTC，用户在东八区。

**决策**：所有"营业日 / 餐次 / 截止时刻"必须经 `campusDate` / `campusClock` / `campusMealType` / `campusTime` 计算，禁止直接 `new Date().getDate()`。

**理由**：
- UTC 16:00 是北京时间次日 00:00，直接用 UTC 日期会导致"晚上下的单算到昨天"
- `getUTCHours() + 8` 这种手写偏移在跨日时会算出 24 点，已经踩过

**代价**：
- 数据库 `@db.Date` 存的是 UTC 零点，读出来要 `toISOString().slice(0,10)` 提取日期部分（**不要再转时区**）
- **PostgreSQL 会话时区已经是 Asia/Shanghai**，写 SQL 时 `now()` 就是北京时间，**不要加 `interval '8 hours'`**，否则跨天

## ADR-009 · 视觉统一靠 CSS 变量，不引入 UI 库

**背景**：是否用 Ant Design / shadcn 加速开发？

**决策**：手写 Tailwind + 一组 CSS 变量（`--sg-orange` `--sg-surface` 等）+ 少量自建组件（`sg-card` / `sg-input` / `sg-btn`）。

**理由**：
- 校园产品的视觉识别度靠"不像后台管理系统"，UI 库默认风格会拉低质感
- 需要品牌色（橙 #F97316 + 深绿）+ 插画风格，UI 库定制成本高于手写
- 包体积：不引 UI 库，首屏 JS 更小

**代价**：
- 组件复用靠约定，没有类型约束
- 表单校验、弹窗等要自己写

## ADR-010 · 只在测试库跑集成测试，绝不连生产

**背景**：集成测试会 `TRUNCATE`、并发扣库存。

**决策**：测试脚本自建一次性 Postgres 容器，**库名必须以 `_test` 结尾**，否则测试直接抛错拒绝运行。

**理由**：
- 有 `ORDER_TEST_DATABASE_URL` 被误设成生产地址的风险
- 库名白名单（`/^\/[a-z][a-z0-9_]*_test/`）是最低成本的保险

**代价**：
- 每次跑测试要起容器（约 5 秒），比连固定测试库慢
- 需要本地有 Docker
