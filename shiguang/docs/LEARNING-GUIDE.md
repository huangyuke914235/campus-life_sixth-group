# 技术学习指南（写给不熟悉 Web 开发的人）

> 目标：读完这篇，你能看懂这个项目大概在干什么、每个技术名词对应什么、出问题时该往哪儿找。
> **不要求你会写代码**，但要求你能对着代码目录说出"这块是管什么的"。

---

## 一、先建立一个整体印象

### 1.1 这个项目在做什么

一句话：**一个帮你决定今天吃什么的网站**。

但它不是"随机推荐"，而是：

```
知道你口味（你填过问卷）
知道你预算（你设过 15-25 元）
知道你忌口（你说过不吃香菜）
知道你上次给哪道菜打了 9 分
     ↓
从 59 道菜里挑出 3 道，告诉你为什么是它们
```

### 1.2 用一家餐厅来类比整个系统

| 现实中的餐厅 | 这个项目 |
|---|---|
| **餐厅招牌和菜单**（你看到的部分） | **前端**（`apps/web`，你浏览器里看到的页面） |
| **后厨**（你看不到，但菜从这里出来） | **后端**（`apps/api`，处理数据、算推荐） |
| **仓库**（存食材的地方） | **数据库**（PostgreSQL，存菜品、订单、评价） |
| **老板定的规矩**（比如"香菜不能给不吃香菜的人"） | **推荐算法**（`packages/shared`） |
| **门口保安查会员卡** | **登录认证**（Cookie） |

**关键认知**：你在浏览器里点的每一个按钮，背后都是"前端发请求 → 后端查数据库 → 后端算结果 → 返回给前端显示"。

## 二、跟着一个请求走一遍（最重要的一节）

场景：你在首页点了「**帮我选这一餐**」。

### 第 1 步：前端发请求

浏览器执行这段代码（`apps/web/src/app/recommend/page.tsx`）：

```ts
post('/recommendations/query', { mealType: 'LUNCH', limit: 3 })
```

意思是："后端你好，给我 3 道午餐推荐。"

**注意**：前端**不知道**该推荐什么，它只负责"问"和"显示"。

### 第 2 步：请求到达后端

请求先到 **nginx**（门卫），nginx 看路径是 `/api/v1/...`，转给 **api 容器**（后厨）。

后端收到后，先过三道关：

| 关卡 | 干什么 | 对应代码 |
|---|---|---|
| ① 你是不是登录了 | 检查 Cookie 里的 `access_token` | `JwtAuthGuard` |
| ② 你是什么角色 | 学生？商户？管理员？ | `RolesGuard` |
| ③ 数据格式对不对 | 参数类型、必填项 | `ValidationPipe` + DTO |

**如果第 ① 关没过** → 返回 401（未登录）。这就是"登录后立刻退回登录页"的技术原因。

### 第 3 步：后端查数据库

后端要回答一个问题：**"今天午餐有哪些菜在卖？"**

它执行一个查询（`recommendations.module.ts` 的 `loadCandidates`）：

```sql
-- 简化后的意思
SELECT 菜品
FROM 菜单项
WHERE 菜单的日期 = 今天
  AND 菜单的餐次 = 'LUNCH'
  AND 菜单已发布
  AND 菜品在售
  AND 档口营业中
```

**这一步最容易出问题**：如果"今天"没有菜单（比如商户忘了发布），查出来就是 0 条，后面全白搭。

### 第 4 步：算法过滤和打分

拿到候选菜（比如 20 道）后，算法做两件事：

**① 硬过滤**（不符合的直接扔掉）

```
过敏原 → 扔
你说不吃香菜 → 含香菜的扔
超出预算 25 元 → 扔
已售罄 → 扔
```

**② 打分排序**（剩下的按分数排）

七个维度各打 0-1 分，加权求和：

```
口味匹配  × 0.30   ← 你爱吃辣，这道菜辣度 4/5 → 0.9 分
饮食习惯  × 0.20   ← 你是素食者，这道菜有肉 → 0 分（而且早被硬过滤扔了）
你的反馈  × 0.15   ← 你给类似的菜打过 9 分 → 0.9 分
菜品质量  × 0.10   ← 这道菜平均 8.7 分 → 0.87 分
预算匹配  × 0.10   ← 18 元，在你 15-25 元区间 → 1 分
餐次供应  × 0.10   ← 午餐有供应 → 1 分
多样性    × 0.05   ← 和你最近吃的重复了 → 0.5 分
```

### 第 5 步：生成"为什么推荐它"

对每道入选的菜，把**实际生效的条件**拼成一句话：

```
"18 元，在你设的 15–25 元内 · 和你偏好的『米饭 + 微辣』一致 · 你上次给类似菜品打了 9 分"
```

**为什么强调"实际生效"**：如果写"符合你的预算"就太空泛了。写具体数字用户才信。

### 第 6 步：返回给前端

后端返回 JSON：

```json
{
  "items": [
    { "dishId": "...", "name": "香菇滑鸡饭", "priceCents": 1400, "reason": "..." }
  ]
}
```

**注意 `priceCents`**：单位是**分**，不是元。1400 分 = 14 元。这样存是为了避免小数误差（0.1 + 0.2 在计算机里不等于 0.3）。

### 第 7 步：前端渲染

React 把 JSON 变成你看到的卡片。

**如果这一步出错**，常见表现：
- 白屏 → 前端代码报错
- 有骨架屏一直转 → 请求没回来
- 显示"暂无数据" → 后端返回了空数组

**到这里，一个完整请求就走完了。** 后面所有功能都是这个模式的变体。

## 三、六个核心技术点（用类比讲）

### 3.1 前端与后端分离：为什么不是"一个东西"

**类比**：餐厅的"点餐台"和"后厨"是分开的两个区域。

**技术上的原因**：

| 分开的好处 | 具体到本项目 |
|---|---|
| 前端可以换（网页 → 小程序 → App） | 后端 API 不用动 |
| 后端逻辑只有一份 | 推荐算法不会在前端和后端各写一遍 |
| 安全 | 数据库密码只存在后端，前端拿不到 |

**代价**：要起两个进程（3000 和 3001 端口），部署复杂一点。

### 3.2 数据库：数据存在哪

**类比**：仓库，有货架（表）、有标签（字段）。

本项目最关键的三张表：

```
Dish（菜品）
  id          编号
  name        菜名
  priceCents  价格（分）
  spiceScore  辣度 0-5
  stallId     属于哪个档口

Menu（菜单）
  date        哪一天
  mealType    哪一餐（早餐/午餐/晚餐）
  stallId     哪个档口的菜单
  @@unique([stallId, date, mealType])   ← 一个档口一天一餐只能有一个菜单

Inventory（库存）
  dishId      哪个菜
  date        哪一天
  total       今天做了多少份
  remaining   还剩多少份
  @@unique([dishId, date, mealType])    ← 一个菜一天一餐只有一个库存记录
```

**`@@unique` 是什么**：数据库层面的"唯一约束"。比如库存表规定"同一个菜+同一天+同一餐只能有一条记录"，插入第二条就会报错。这是**防重复的最后一道保险**。

**为什么库存按天独立**：昨天的剩余不能算到今天的。食堂每天都重新备货。

### 3.3 推荐算法：为什么不用 AI

**类比**：一个老师傅凭经验打分，而不是问一个会编故事的年轻人。

**技术上的三个原因**：

1. **可解释**：每个理由必须能追溯到具体字段。"你设的预算 15-25 元"是查出来的，"我觉得你会喜欢"是编的。
2. **确定性**：同样的输入必须得到同样的输出。否则没法测试，出了问题也没法复现。
3. **成本**：饭点每小时上千次请求，调 AI 接口的成本扛不住；而且食堂网络不稳定，断网就瘫痪。

**代码位置**：`packages/shared/src/recommendation.ts`

**为什么放在 `shared` 而不是后端**：因为前端也要用同一套类型定义，而且算法是纯函数，单独拿出来能直接跑单元测试，不需要数据库。

### 3.4 登录认证：Cookie 是什么

**类比**：进小区时保安给你一张门禁卡，之后每次进门刷卡就行，不用重新登记。

**Cookie 就是那张卡**：

```
你登录 → 后端给你一张"卡"（Set-Cookie: access_token=xxx）
       → 浏览器自动存起来
你之后再点任何按钮 → 浏览器自动带上这张卡（Cookie: access_token=xxx）
       → 后端一看卡有效，知道是你
```

**这张卡有三个安全属性**（这就是那天登录失败的根源）：

| 属性 | 作用 | 配错的后果 |
|---|---|---|
| `HttpOnly` | JS 读不到这张卡 | 防 XSS 攻击，基本都要开 |
| `Secure` | 只在 HTTPS 下才发送 | **HTTP 下浏览器直接不存** → 登录失败 |
| `Domain` | 这张卡属于哪个域名 | **IP 访问时域名不匹配 → 浏览器直接丢弃** → 登录失败 |

**那天的三个坑**：
1. `Secure=true` + HTTP 访问 → 卡存不下来
2. `Domain=campus-life.ccwu.cc` + 用 IP 访问 → 卡不属于这个地址，被丢弃
3. CSRF 令牌也依赖 Cookie → 跟着一起坏

### 3.5 事务：一次性做完，否则全不做

**类比**：转账。从 A 扣 100 元、给 B 加 100 元，这两步必须同时成功，不能只做一半。

**本项目的例子**：下单要同时做四件事：

```
① 扣库存（remaining - 1）
② 占时段名额（booked + 1）
③ 创建订单记录
④ 生成取餐码
```

**如果第 ③ 步失败**，前两步必须撤销，否则会出现"库存少了但没订单"。

**技术实现**：`prisma.$transaction()`（`withSerializable` 封装）。

**并发问题**：两个人同时抢最后一份怎么办？

```
错误做法：先查"还剩 1 份"，再扣减  ← 两个人都查到 1 份，都扣，变成 -1
正确做法：条件更新"如果还剩 ≥1 就扣 1"  ← 数据库保证只有一个人成功
```

代码长这样：

```ts
const updated = await tx.inventory.updateMany({
  where: { dishId, remaining: { gte: 1 } },   // 条件是"还剩至少 1 份"
  data: { remaining: { decrement: 1 } },
});
if (updated.count !== 1) throw new Error('库存不足');  // 没更新到就是抢失败了
```

**验证结果**：20 个人同时抢 1 份，只有 1 个人成功（这个测试真的跑过）。

### 3.6 部署：把店开到大街上

**类比**：在自己家厨房做饭（本地开发）vs 租个店面挂牌营业（部署上线）。

本项目用的是 **Docker**：把"前端 + 后端 + 数据库 + nginx"打包成几个"集装箱"，整个搬到服务器上跑。

```
你的电脑                          服务器（Azure VM）
┌──────────────┐                ┌──────────────────────┐
│ 写代码        │                │  nginx（门卫）        │
│ 本地测试      │  ── 打包 ──▶   │  ├─ web 容器（前端）   │
│              │                │  ├─ api 容器（后端）   │
└──────────────┘                │  ├─ postgres（数据库） │
                                │  └─ redis（缓存）      │
                                └──────────────────────┘
```

**为什么用 Docker**：服务器上不需要装 Node.js、PostgreSQL，只要装 Docker 就行。而且"我电脑上能跑"和"服务器上能跑"的环境完全一致。

**常见的部署坑**（都踩过）：

| 坑 | 现象 | 原因 |
|---|---|---|
| 改了代码没生效 | 服务器上还是旧功能 | 改了镜像里的文件但没**重建镜像** |
| 页面 502 | 打不开 | 后端容器重建后 IP 变了，nginx 还指着旧 IP → **要重启 nginx** |
| 环境变量没生效 | 配置改了没用 | 前端有些变量是**构建时写死**的，运行时改无效 |

## 四、代码导航：从哪开始读

### 4.1 目录结构

```
shiguang/
├── apps/
│   ├── web/              ← 前端（你在浏览器看到的）
│   │   └── src/
│   │       ├── app/      ← 每个文件夹 = 一个页面
│   │       │   ├── page.tsx          首页
│   │       │   ├── recommend/        推荐页
│   │       │   ├── checkout/         结算页
│   │       │   └── admin/            后台
│   │       ├── components/   ← 可复用组件（卡片、导航栏）
│   │       └── lib/api.ts    ← 所有请求都从这里发
│   │
│   └── api/              ← 后端（处理数据、算推荐）
│       └── src/
│           ├── dishes/         菜品
│           ├── orders/         订单（最复杂）
│           ├── recommendations/ 推荐
│           ├── reviews/        评价
│           └── common/         公共工具（错误码、权限、日志脱敏）
│
├── packages/shared/      ← 前后端共用（算法在这里）
│   ├── src/recommendation.ts   推荐算法核心
│   └── src/order.ts            订单规则（金额、状态机）
│
├── prisma/
│   ├── schema.prisma     ← 数据库表结构定义
│   └── migrations/       ← 建表脚本
│
└── docs/                 ← 文档（本文件在这）
```

### 4.2 推荐阅读顺序

| 顺序 | 读什么 | 为什么 |
|---|---|---|
| 1 | `docs/PRD.md` | 先知道"做什么" |
| 2 | 本文档第二节的"请求走一遍" | 建立全局流程感 |
| 3 | `prisma/schema.prisma` | 看数据长什么样（最直观） |
| 4 | `packages/shared/src/recommendation.ts` | 算法（纯函数，不依赖数据库） |
| 5 | `apps/api/src/orders/orders.module.ts` | 最复杂的业务逻辑（事务、并发） |
| 6 | `apps/web/src/app/page.tsx` | 前端怎么调接口 |

**不建议从** `apps/web/src/components/` 开始——那里全是 UI 细节，容易迷失。

### 4.3 常见修改该去哪里

| 你想改 | 改哪里 |
|---|---|
| 推荐权重（比如更重视预算） | `packages/shared/src/recommendation.ts` 的 `DEFAULT_WEIGHTS` |
| 推荐理由的文案 | 同一个文件的 `reason` 生成部分 |
| 某个接口的返回字段 | 对应 `apps/api/src/xxx/xxx.module.ts` |
| 页面布局/颜色 | `apps/web/src/app/xxx/page.tsx` + `tailwind.config.ts` |
| 数据库加字段 | `prisma/schema.prisma` → 跑迁移 |
| 菜品图片匹配规则 | `apps/web/src/lib/dish-image.ts` |

## 五、术语表（小白版）

| 术语 | 大白话 |
|---|---|
| **前端** | 你看到的页面 |
| **后端** | 你看不到的、处理数据的程序 |
| **API** | 前端和后端说话的约定（"给我 3 道菜" → "给你这 3 道"） |
| **数据库** | 存数据的地方 |
| **表** | 数据库里的一类数据（菜品表、订单表） |
| **字段** | 表里的一列（菜名、价格） |
| **主键 id** | 每条数据的唯一编号 |
| **唯一约束** | 规定某几列的组合不能重复（比如同一天同一档口只能有一个菜单） |
| **事务** | 一组操作要么全成功要么全失败 |
| **并发** | 很多人同时操作 |
| **Cookie** | 浏览器存的一小段数据（登录凭证） |
| **JWT** | 一种"防伪令牌"的格式，后端签发，前端不用懂内容 |
| **Docker** | 把程序打包成"集装箱"，到哪都能跑 |
| **容器** | 一个跑起来的"集装箱" |
| **镜像** | 集装箱的"模板"（改了代码要重新打包成镜像） |
| **nginx** | 门卫，负责把请求转给对应的服务 |
| **环境变量** | 不改代码就能改的配置（密码、开关） |
| **迁移（migration）** | 改数据库结构的脚本 |
| **seed** | 灌初始数据的脚本（本项目会清库重灌，危险） |
| **哈希（hash）** | 把密码变成一串看不懂的字符，存这个而不是明文 |

## 六、如果只能记住三件事

**① 前端只负责"问"和"显示"，所有判断都在后端**

你在页面上看到的每个数字、每条理由，都是后端算出来传过去的。前端不能"自己决定推荐什么"。

**② 出了问题先分层定位**

```
页面打不开 → 前端问题？nginx 问题？后端挂了？
页面能开但没数据 → 后端返回空？数据库没数据？过滤条件太严？
登录不了 → Cookie 没下发？浏览器没存？没回传？
```

**② 补充：看日志比看代码快**

```bash
docker compose logs api --tail 50
```
90% 的问题，日志里第一行就写着原因。

**③ 数据库是唯一的真相**

页面显示可能骗人（缓存、旧数据），但数据库里的行数不会骗人。**怀疑数据不对时，直接查表**。

## 七、下一步怎么学

如果你真想看懂代码，按这个顺序动手：

1. **跑起来**：按 `docs/DEPLOYMENT.md` 在本地起一套，能看到页面
2. **改文案**：把首页"今天吃什么"改成别的字，看页面变不变（验证前后端关系）
3. **看一个接口**：F12 → Network → 点一个按钮，看请求和响应
4. **加一个字段**：给 `Dish` 加个 `辣度描述`，走一遍 schema → 迁移 → 接口 → 页面的完整链路
5. **写一个测试**：给推荐算法加一条测试用例，看它能不能跑

**第 4 步是最有价值的**——走通一次"数据从数据库到页面"的完整链路，你对整个项目的理解就建立了。
