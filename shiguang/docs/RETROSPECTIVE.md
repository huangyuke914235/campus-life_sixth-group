## 二、五个关键转折点

### 转折 1 · 口味选项与真实数据脱节（11-11 上午）

**发生了什么**：问卷选项是「爱米饭面食 / 无肉不欢」，但真实菜品是 59 道米线、烧腊、湘菜、螺蛳粉。

**当时的选择**：降级方案——不采集真实菜品数据，用通用选项。

**后果**：选项与数据对不上，推荐逻辑无从匹配，整个产品的地基是空的。

**学到什么**：

> **降级方案如果不能和真实数据对上，比没有更糟。**
> 宁可推迟两天把数据补齐，也不要用假选项撑起真功能。

**正确做法**：先把 13 个食堂的 59 道菜录进去，再按菜品特征反推该有哪些选项。

---

### 转折 2 · 推荐 0 道 + 评价 0 条（11-11 上午）

**发生了什么**：菜单、评价、画像全是 0，只有菜品 59 条。

**排查过程**（花了 2 小时）：

1. 以为是数据没跑 → 重跑 seed，报同样的错
2. 以为是镜像旧 → 重建镜像再跑，还是一样
3. 打开 `seed.ts` 数了一遍 `userPreference.create` → **10 处**，正常应该 6 处

**根因**：之前用 Python 脚本插入代码时**没有限制替换次数**，同一段画像代码被插了两遍。第 7 个 `create` 撞 `userId` 唯一约束 → seed 事务回滚 → 后面的菜单、库存、评价全没执行。

**学到什么**：

> **任何自动改代码的操作，必须限定替换次数并断言唯一性。**
> `str.replace(old, new)` 默认替换**所有**匹配，这是 Python 的默认行为，不是 bug。

**后续动作**：之后所有 Python 替换都加 `assert s.count(old) == 1`，这个习惯在后续 10 多次修改里救了命（多次避免了改乱文件）。

---

### 转折 3 · IP 访问登录失败（11-11 下午）

**发生了什么**：评审平台只给 IP，站点突然登不上，但登录接口返回 200。

**排查过程**（三连坑，逐个暴露）：

| # | 问题 | 现象 | 修法 |
|---|---|---|---|
| 1 | `COOKIE_SECURE=true` | HTTP 下浏览器拒存 Cookie | 改 `false` |
| 2 | `COOKIE_DOMAIN=campus-life.ccwu.cc` | 用 IP 访问时 Domain 不匹配，Cookie 被**直接丢弃** | 删掉这行 |
| 3 | CSRF 双提交依赖 Cookie | 前两个坏时它也一起坏 | 随 1、2 一起修 |

**关键细节**：第 2 个坑修完**第 1 个坑的修复才生效**——因为 Domain 不匹配时，浏览器连 Cookie 都不接收，Secure 属性根本轮不到判断。

**学到什么**：

> **配置类问题要按"数据流向"逐层验证，不要跳步。**
> 正确顺序是：服务端有没有下发 → 浏览器有没有接收 → 有没有回传 → 服务端有没有认出。

**留下的资产**：`OPERATIONS.md` 的 2.2 节，一条 `curl` 命令就能验证 Cookie 是否带 `Secure`/`Domain`。

### 转折 4 · 第三方审计报告（11-11 中午）

**发生了什么**：拿到一份 367 行的审计报告，4 个 P0 / 6 个 P1 / 4 个 P2。

**最刺痛的一条**：

> 「`Partial<DishDto>` 在运行时是 `Object`，全局 DTO 校验因此跳过该请求体。Prisma 支持关系更新，风险可延伸到档口归属和角色。」

**这意味着**：商户可以通过改菜品，把菜挂到**别人的档口**下。

**验证过程**：写集成测试实际发起跨档口请求 → 确实返回 200 并改了 `stallId`。

**修法**（双保险）：
1. DTO 改成 `PartialType(OmitType(DishDto, ['stallId']))`——真实类，校验生效
2. Service 层加白名单——即便校验被绕过也拦得住

**学到什么**：

> **TypeScript 的类型只在编译期有效，运行时是另一回事。**
> 任何"从前端来的数据"都要在**运行时**再校验一次，不能依赖类型标注。

**更深的教训**：这个漏洞**单元测试永远测不出来**（类型系统挡住你写测试代码），只有**集成测试**（用 `as never` 强制传非法字段）才能暴露。

### 转折 5 · 跨天推荐为空（11-15）

**发生了什么**：11-13 部署完能用，11-14 打开推荐 0 道。

**根因**：`loadCandidates` 按**当天日期**查 `Menu`，而菜单是 11-11 seed 出来的。跨天就查不到。

**修复中的三次失败**：

| 尝试 | 报错 | 根因 |
|---|---|---|
| 1 | 无报错但没效果 | `DO $$` 单事务，`m.id \|\| i`（text \|\| int）类型错误导致整体回滚 |
| 2 | `null value in column "updatedAt"` | Prisma `@updatedAt` 在 DB 层无默认值，裸 SQL 必须显式给 |
| 3 | 生成到了明天 | 数据库会话时区已是 `Asia/Shanghai`，我又加了 `interval '8 hours'` |

**学到什么**：

> **`DO $$` 块是单事务，任何一处报错都是"静默无效果"——看起来执行了，其实全回滚了。**
> 调试时要看 `NOTICE` 输出，不能只看"命令返回 0"。

> **时区问题要分清"存储时区"和"会话时区"。**
> 这个项目里：DB 会话是上海时区、Node 进程是 UTC、`campusDate()` 手动 +8 小时。三套时间逻辑并存，是 bug 温床。

**留下的资产**：`OPERATIONS.md` Q1 的完整 SQL，以及"不要加 8 小时"的红字警告。

## 三、十类经验教训

### 3.1 关于「演示」与「生产」

| 教训 | 案例 |
|---|---|
| **演示环境的临时手段会变成永久债务** | 为了演示自动 seed，结果每次重启清库 |
| **"能演示"和"能上线"是两件事** | 演示只走主路径；上线要考虑并发、权限、数据安全 |
| **给评委的链接要按最差的网络环境设计** | 只给 IP 就必须放弃 HTTPS，进而放弃 Secure Cookie |

**原则**：从第一天就明确"这是演示还是要上线"，两者的技术选择差别很大。**最怕的是按演示写、按上线用**。

### 3.2 关于「数据」

| 教训 | 案例 |
|---|---|
| **假数据比没数据更危险** | 56 道假菜名撑着推荐，一换成真数据全崩 |
| **数据要能自己解释自己** | 菜品标了"辣度 0-5"，推荐才能算"口味匹配" |
| **清理数据的脚本必须幂等** | `TRUNCATE` + `create` 改成 `upsert`，才不会重复插入 |

### 3.3 关于「测试」

| 教训 | 案例 |
|---|---|
| **单元测试测不出权限漏洞** | 类型系统挡住你写"传非法字段"的测试代码 |
| **集成测试必须连真实数据库** | Mock 出来的 Prisma 永远不报唯一约束冲突 |
| **测试跳过要显式告警** | `describe.runIf(Boolean(url))` 静默跳过，看起来"全绿"其实没测 |
| **测试库要有名字白名单** | 库名必须 `*_test`，否则可能连到生产库 `TRUNCATE` |

### 3.4 关于「部署」

| 教训 | 案例 |
|---|---|
| **改镜像内的文件必须重建镜像** | `docker compose exec` 跑的是镜像里的旧文件，宿主机改了不生效 |
| **容器重建后 nginx 必须重启** | 上游 IP 变了，502 |
| **环境变量三个来源要分清** | `.env` / compose `environment` / Dockerfile `ARG`，优先级容易搞混 |
| **Next 的 `NEXT_PUBLIC_*` 是构建期内联** | 运行时改环境变量无效 |

### 3.5 关于「安全」

| 教训 | 案例 |
|---|---|
| **私钥必须在第一天就 gitignore** | 这次是审计报告指出来的，如果先提交过就麻烦了 |
| **响应字段要显式 select** | 直接返回 `update` 结果会带出 `passwordHash` |
| **Cookie 的 Domain/Secure/SameSite 三件套** | 任一配错表现都是"登录不了" |
| **演示开关要有"生产拒绝"守卫** | `SEED_DEMO_DATA=true` 在生产必须启动失败 |

### 3.6 关于「文档」

| 教训 | 案例 |
|---|---|
| **文档过期比没有更糟** | `TESTING.md` 写着"27/27、集成未运行"，实际早已 45+20 |
| **文档要写"为什么"，不只是"是什么"** | `ADR.md` 的 10 条决策，每条都有"代价" |
| **操作手册要写到"点哪里"** | "进入偏好设置" vs "我的 → 口味设置 → 第 1 步" |
| **踩坑记录是最有价值的文档** | `HANDOVER.md` 第 6 章的 8 个坑，每个都能复现 |

### 3.7 关于「与 AI 协作」

| 教训 | 案例 |
|---|---|
| **AI 会自信地给出错误的操作** | 用 `replace` 没限次数，改乱文件 |
| **必须要求"实测证据"，不接受"应该没问题"** | 每次改完都跑 tsc + 测试 |
| **让 AI 做审计要明确"只读"** | 否则它会顺手改代码，掩盖问题 |
| **关键决策要人来拍板** | 技术选型、架构变更，AI 只提供选项和代价 |

### 3.8 关于「调试方法」

| 教训 | 案例 |
|---|---|
| **先分层定位，再动手** | 推荐 0 道：先查数据（59 菜在）→ 再查过滤（全排）→ 最后查代码 |
| **看日志不要只看最后一行** | `DO $$` 块的 `ERROR` 在中间，最后一行是 `DO` |
| **"命令返回 0"不等于成功** | `docker exec` 缺 `-i`，psql 空跑也返回 0 |
| **对比时间线** | "昨天能用今天不能用" → 一定是环境或数据变了 |

### 3.9 关于「时间管理」

| 教训 | 案例 |
|---|---|
| **功能写完只占 20% 时间** | 9 天里 3 天写代码，6 天修问题和写文档 |
| **修一个问题可能引出三个** | IP 登录失败暴露了三个叠加的配置问题 |
| **留出"上线后第一天"的时间** | 跨天推荐为空，是部署第二天才发现的 |

### 3.10 关于「与评审方沟通」

| 教训 | 案例 |
|---|---|
| **平台的约束要在设计前问清楚** | 只给 IP 链接 → 整个认证方案要改 |
| **提前准备"为什么不是 https"的答案** | 域名已配好，但平台限制只能填 IP |

## 五、可迁移的方法论

### 5.1 「三层验证法」

任何改动，按顺序验证：

```
① 编译层：tsc / build 过不过
② 单元层：纯函数的行为对不对
③ 集成层：连真实数据库/浏览器，行为对不对
```

**只有第 ③ 层过了，才能说"能用"。** 这次所有坑里，没有一个是 ① ② 能发现的。

### 5.2 「唯一锚点替换法」

改代码时：

```python
# ❌ 危险
s = s.replace(old, new)

# ✅ 安全
assert s.count(old) == 1, f'匹配 {s.count(old)} 次'
s = s.replace(old, new, 1)
```

**更进一步**：用包含函数名/类名的长上下文做锚点，而不是单个语句。

### 5.3 「配置问题排查顺序」

```
服务端有没有生成 → 传输过程有没有丢 → 客户端有没有接收 → 客户端有没有回传 → 服务端有没有认出
```

对应到 Cookie：`Set-Cookie` 有没有 → 有没有 Secure/Domain 干扰 → 浏览器 Application 面板有没有 → 下一请求带没带 → 后端日志有没有认出来。

### 5.4 「静默失败识别法」

以下现象都可能是"静默失败"：

| 现象 | 可能原因 |
|---|---|
| 命令返回 0 但没效果 | 管道/heredoc 没传进去 |
| SQL 跑完没变化 | `DO` 块整体回滚 |
| 测试全绿 | 用例被 skip |
| 日志说"已完成" | 是脚本自己 echo 的，不是真实结果 |

**对策**：每条关键操作后**立刻查一次真实状态**（行数、文件是否存在、接口返回什么）。

### 5.5 「文档分层法」

| 层 | 面向 | 内容 | 本项目对应 |
|---|---|---|---|
| 产品层 | 评审/产品 | 为什么做、给谁做、不做什么 | `PRD.md` |
| 决策层 | 架构/技术负责人 | 为什么这么选、代价是什么 | `ADR.md` |
| 设计层 | 开发 | 模块、数据流、表结构、接口 | `ARCHITECTURE` / `DATABASE` / `API` |
| 操作层 | 用户/运维 | 点哪里、命令是什么、出问题怎么办 | `USER_GUIDE` / `OPERATIONS` |
| 过程层 | 接手的人 | 做了什么、踩了什么坑 | `CHANGELOG` / `HANDOVER` |

**缺任何一层都会有盲区**：只有设计层 = 新人不知道怎么用；只有操作层 = 不知道为什么这么设计。
