## 一、背景与问题

### 1.1 真实场景

深圳大学粤海、丽湖两校区共 13 个食堂，日均供餐窗口数量上百。学生的日常困境不是"没得吃"，而是：

| 困境 | 具体表现 |
|---|---|
| **信息不对称** | 菜单贴在窗口，学生走到现场才知道今天有什么；跨楼层跑一圈才发现想吃的没有 |
| **决策成本高** | 高峰期排队时只能"随便点一个"，事后后悔 |
| **口味不匹配** | 同一道菜不同窗口做法差异大，第一次踩雷只能自认倒霉 |
| **忌口无处标注** | 过敏、宗教饮食、素食需求只能靠问窗口阿姨，信息不透明 |
| **反馈无去处** | 吃完想说"太咸了"，没有渠道，下一次还是一样 |

### 1.2 现有方案为什么不够

| 方案 | 问题 |
|---|---|
| 大众点评 / 美团 | 面向校外商家，校园食堂没有入驻；评分是"人均消费"逻辑，不是"这一餐"逻辑 |
| 学校后勤公众号 | 只发通知，没有结构化菜单，不能筛选 |
| 微信群问同学 | 信息碎片化，不可检索 |
| 食堂门口菜单牌 | 静态，不区分时段，不标价格和辣度 |

**核心缺口**：没有把「食堂的真实菜单」变成「可检索、可筛选、可反馈的结构化数据」。

## 二、目标用户与场景

### 2.1 三类角色

| 角色 | 是谁 | 核心诉求 |
|---|---|---|
| **学生**（主用户） | 在校本科生/研究生 | 3 秒内决定吃什么，别踩雷 |
| **商户** | 档口经营者 | 让菜被看见，知道哪道菜卖得好，控制备餐量 |
| **管理员** | 食堂管理者 / 平台运营 | 掌握整体经营数据，处理异常 |

### 2.2 核心场景（按频次排序）

**场景 A：饭点决策（每天 2 次，最高频）**

> 11:40，下课。学生打开站点，首页直接出 3 道推荐菜，每道标注「为什么推荐它」（口味匹配 / 预算内 / 你上次给过 9 分）。点「换一批」或选场景标签（想吃辣 / 清淡一点 / 便宜点）微调。选定后看档口位置和价格，决定去不去。

**关键要求**：**3 秒内给出答案**，不要让学生自己翻列表。

**场景 B：下单预约（每天 0.3 次）**

> 想吃某个热门档口但怕排队。提前下单选 12:00 的取餐时段，到点直接报取餐码取走。

**关键要求**：库存和时段容量必须真实，不能出现"下了单没菜"。

**场景 C：饭后反馈（每天 0.15 次）**

> 吃完觉得"这个番茄炒蛋偏咸"。10 星打分 + 勾体感标签（偏咸 / 分量足），可选写一句短评。

**关键要求**：**10 秒内能完成**，超过 3 步就没人填。

**场景 D：商户发布菜单（每天 1 次）**

> 早上开档前，商户在后台把今天供应的菜挂到菜单上，设置库存和取餐时段。

**关键要求**：批量操作，不能一道菜一道菜点。

**场景 E：管理员看数据（每周 1 次）**

> 周末看本周各档口的预约量、完成率、取消率、哪道菜评分最低。

## 三、功能范围

### 3.1 学生端（P0）

| 功能 | 说明 | 优先级 |
|---|---|---|
| 注册 / 登录 | 邮箱 + 密码，注册后引导设口味 | P0 |
| 口味问卷 | 3 步：基础口味 / 辣度油盐 / 预算忌口，约 1 分钟 | P0 |
| 个性化推荐 | 3 道菜 + 「为什么推荐它」，含口味、预算、营养三个维度理由 | P0 |
| 场景微调 | 想吃辣 / 清淡一点 / 高蛋白 / 来点汤 / 便宜点 / 尝点新菜 | P1 |
| 菜品浏览 | 分页、按食堂/分类筛选、搜索 | P0 |
| 菜品详情 | 价格、位置、营养成分、过敏原、历史评价 | P0 |
| 下单预约 | 选时段、库存校验、幂等提交 | P0 |
| 取餐码 | 下单后生成，档口核销 | P0 |
| 评价 | 10 星打分 + 体感标签 + 短评 | P0 |
| 收藏 | 标记常吃的菜 | P2 |
| 饮食记录 | 近 30 天吃过什么、营养摄入 | P2 |

### 3.2 商户端（P0）

| 功能 | 说明 |
|---|---|
| 菜单管理 | 按日期餐次挂菜、设置库存、发布 |
| 取餐时段 | 设置时段和容量 |
| 待处理订单 | 接单、备餐、待取餐 |
| 核销 | 输入/扫码取餐码，一码只能核销一次 |
| 菜品编辑 | 改价格、描述、辣度/油腻/咸度、过敏原 |

### 3.3 管理端（P1）

| 功能 | 说明 |
|---|---|
| 档口授权 | 分配 MERCHANT 角色并绑定档口 |
| 经营统计 | 按营业日、档口、订单状态聚合 |
| 评价审核 | 隐藏违规评价 |
| 操作审计 | 改角色、改菜品、审核记录 |
| 公告 | 发布系统通知 |

### 3.4 明确不做（边界）

| 不做 | 原因 |
|---|---|
| **在线支付** | 校园场景到店付款已是习惯，接入支付需要资质和分账，成本远超收益 |
| **外卖配送** | 食堂就在楼下，配送没有价值 |
| **社交功能**（评论点赞、好友） | 偏离"决策工具"定位，会稀释核心体验 |
| **多校区 / 多学校** | 首版只服务深大，跨校需要完全不同的数据治理 |
| **AI 大模型生成推荐理由** | 推荐理由必须可解释、可追溯，模板化理由比"AI 编的话"更可信，也省成本 |
| **菜品图片上传** | 首版用 12 张分类图按菜名映射，避免商户拍出参差不齐的照片 |

## 四、核心设计原则

### 4.1 三条不可妥协的原则

**① 推荐必须可解释**

每道推荐菜都要给出「为什么是它」，且理由必须引用**实际生效的条件**（比如"你设的预算 15–25 元"而不是"符合你的预算"）。用户不信的理由等于没有理由。

**② 忌口是硬约束，不是偏好**

过敏原、宗教饮食、明确标注的忌口，**永远过滤，不做加权**。系统的"智能"不能覆盖用户的安全。

**③ 数据要真**

菜品价格、位置、营业时间全部来自食堂实际数据。**不做假数据**——一旦用户发现推荐的是不存在的菜，整个产品的信任就没了。

### 4.2 交互约束

| 约束 | 数值 | 理由 |
|---|---|---|
| 首页推荐出结果 | ≤ 3 秒 | 饭点排队时没有耐心 |
| 评价完成步骤 | ≤ 3 步 | 超过就没人填 |
| 口味问卷 | ≤ 1 分钟 | 注册流失率的关键 |
| 推荐条数 | 3 条 | 5 条以上选择困难又回来了 |

## 五、成功指标

### 5.1 核心指标（试点期）

| 指标 | 定义 | 目标 |
|---|---|---|
| **推荐采纳率** | 看了推荐并下单推荐菜品的学生数 ÷ 看过推荐的学生数 | 与"热门菜基线"对比，**显著更高**才算成功 |
| 有效预约成功率 | 未被系统取消的订单数 ÷ 按幂等键去重后的请求数 | > 95% |
| 取餐完成率 | `PICKED_UP` 订单数 ÷ 有效预约数 | > 85% |
| 评价填写率 | 填了评价的订单数 ÷ 完成订单数 | > 30% |
| 忌口零事故 | 含过敏原的菜被推荐给过敏用户 | **必须为 0** |

### 5.2 反向指标（出现即说明设计有问题）

- 单用户日均推荐刷新次数 > 10 次 → 推荐不准，用户在反复找
- 取消率 > 20% → 库存/时段设置不合理
- 评价平均分持续下滑 → 菜品质量或推荐匹配度有问题

## 六、数据与隐私

| 项 | 处理方式 |
|---|---|
| 收集什么 | 邮箱、口味偏好、评价、订单记录 |
| 不收集什么 | 手机号、地理位置、通讯录、支付信息 |
| 画像用途 | 仅用于本系统推荐，**不对外提供** |
| 删除权 | `DELETE /users/me` 标记删除，30 天后物理清除 |
| 审计 | 管理员改角色、审核评价均写 `AuditLog` |

## 七、演进路线

| 阶段 | 目标 | 关键动作 |
|---|---|---|
| **已完成** | 可演示的完整闭环 | 推荐 / 下单 / 核销 / 评价 / 商户后台 |
| **下一步** | 试点可用 | 商户端「一键复制昨日菜单」、菜单按天自动发布、真实备份演练 |
| **中期** | 稳定运营 | 校园统一认证接入、档口级经营日报、推荐 A/B 对比 |
| **长期** | 可复制 | 多食堂模板化配置、菜品图片标准化流程 |

**不做**：推荐排序引入深度学习。**理由**：试点期数据量只有几百条评价，任何模型都会过拟合；先积累真实数据，再决定是否值得。
